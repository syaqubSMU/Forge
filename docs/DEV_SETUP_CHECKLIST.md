# Dev environment setup checklist (owner)

One page. Variable **names only**: never write a value or secret into this file, a chat or a commit. The Render menu names below are from general knowledge and were NOT checked against the live Render screens; the owner should correct any label that differs. Everything about the application itself is from this repository.

## 1. Service
- [ ] New **Web Service** from this repository, branch `integration` (dev only; main is the live site and is not touched by this).
- [ ] **Root directory:** `backend`
- [ ] **Build command:** `pip install -r requirements.txt`
- [ ] **Start command:** `uvicorn --factory app.main:create_app --host 0.0.0.0 --port $PORT`
- [ ] **One worker.** Do not add `--workers`, and do not scale to more than one instance: the rate limits, the model-call cap, the lookup cache and the daily caps live in each process's memory.
- [ ] **Health check path:** `/api/health` (returns `{"status":"ok", ...}`).
- [ ] Dev and production use **different databases and different passwords**.

## 2. Environment variables (set in the service's Environment tab)
| Name | Required | What it is for | Notes |
|---|---|---|---|
| `FORGE_DB` | yes | Database address | A `postgresql://` URL. For Neon use the **direct** (non-pooled) string. |
| `ADMIN_TOKEN` | yes | Admin sign-in | A long random string you generate. Admin pages and the checks below need it. |
| `FORGE_SALT` | yes | Salt for visitor hashes | A long random string, different from `ADMIN_TOKEN`. The server warns at start if it is missing. |
| `FORGE_API_KEY` | for live runs | Model key | Any of `FORGE_MODEL_KEY`, `FORGE_API_KEY`, `SIGNAL_MODEL_KEY`, `ANTHROPIC_API_KEY` works; use one. Set a spending limit with the model provider. |
| `FORGE_TRUSTED_PROXY_HOPS` | after rehearsal | Trusted proxies in front of the server | Leave unset until the rehearsal in `backend/README.md` finds the right number (expected 1). |
| `FORGE_CORS_ORIGINS` | only if pages are on another address | Page addresses allowed to call the API | Comma-separated. Empty when the server serves the pages itself. |
| `FORGE_MODEL_MAX_CONCURRENT` | optional | Cap on simultaneous model calls, whole process | Default 16. Change only after the two-simultaneous-runs rehearsal. |
| `FORGE_STATIC` | optional | Folder of web pages to serve | Default is `public/signal` in the repository; set only if the pages live elsewhere. |
| `FORGE_EFFORT` | optional | Model effort level | Leave unset (model default) until a larger repeatability check supports `low`. |

## 3. After the first start (admin token goes in the `X-Admin-Token` header; use your own terminal, never paste it into chat)
- [ ] `GET /api/health` returns `status: ok`.
- [ ] `GET /api/admin/environment` shows, without any secret value: `database: postgres`, `schema_version: 2` or higher, `admin_token_set: true`, `salt_set: true`, `model_key_variable` naming the variable you used, `static_dir_found: true`, `trusted_proxy_hops` as intended. If any is wrong, fix the variable and restart.
- [ ] **Switch the model to `claude` (easy to forget).** The default `active_model` is `mock`, which cannot rate anything. Send `PUT /api/admin/settings` with body `{"active_model": "claude"}`. **Pass:** `GET /api/admin/environment` now shows `"active_model": "claude"` and `model_key_variable` names the variable you set. **If a live run returns 502 "The model's answers could not be read", the model is still `mock`** (or the key is wrong: a wrong key gives 502 "could not be reached"); recheck this step and the key.
- [ ] Prices for cost estimates are entered as `price_per_mtok_input` and `price_per_mtok_output` in settings (the owner supplies the numbers).
- [ ] Run `python scripts/ingest.py` once (from `backend/`, `FORGE_DB` set in your shell) so runs read the stored copy; check `GET /api/admin/ingest/status`.
- [ ] Work through the rehearsal checklist in `backend/README.md`, then `FORGE_TRUSTED_PROXY_HOPS` can be set with confidence.

## 3b. Pilot budget (the owner's ceiling is $20 for the WHOLE pilot, spend already made included; live model only when important; if it looks like overrunning, ask the owner)
Assumed pilot window: Dec 2 to 6 (the PRD schedule; the owner did not state a length). Estimates use list prices for `claude-opus-5-5` of $4 per million input tokens and $20 per million output tokens (as of 2026-11-03; the owner confirms them in the provider console). A 25-judgment run is about $0.77 (about 32,000 input and 30,000 output tokens); at **15 judgments about $0.45** (the access-code budget check derives this from `max_judgments` x $0.03 a judgment; the one recorded run measured about $0.48). About $7 is assumed already spent on engineering tests (not in the database), leaving about **$13**.
**Budget allocation (the real constraint):** ceiling $20; about $7.5 spent so far (engineering tests and the recorded run), outside the hosted database; about $12.5 remaining. Plan: 6 testers x 3 runs = 18 runs (about $7.9) + the owner's hosted code of 2 runs (about $0.9) + hosted rehearsal checks (about $1.5) = about **$10.3** of spend in the hosted database (about $10.7 if the owner's code were 3), ending near $17.8 to $18.2 in total and leaving the rest for what the numbers undercount (abandoned or failed calls, and the owner's LOCAL live runs, which the hosted database does not see; they spend this budget too). **The true spending bound is the total of the access-code allowances, not the daily cap.**
**The setting that needs an owner decision (do not change it without asking):** `pilot_budget_usd` is **9.0** and counts only the hosted database. The plan above needs about $10.3 there, so with 9.0 the budget stop (and the check that refuses to create a code that would exceed the budget) would fire roughly 3 runs before the last tester finishes, and creating the last codes could be refused once rehearsal spend is recorded. **Figure to ask the owner for: 10.5** (the planned $10.3 plus a little margin): with about $7.5 already spent elsewhere, 7.5 + 10.5 = $18.0, exactly the point at which all live calls stop. A value of 11.0 would give 18.5, which crosses that $18 stop, so I recommend 10.5, or less if the rehearsal checks are done mostly on a local database.
**`daily_cap`:** the built-in default is 3, which would block six testers who all try on the same day, so it must be **6 during the tester window** (`PUT /api/admin/settings`); it is pacing, not the ceiling. **`require_access_code` is true by default** on the hosted engine, so no live run works until the owner creates a code.
**Sizing the daily cap (recompute it from the real pilot length and the remaining budget):** the daily count resets at UTC midnight, and Dec 2 to 6 in Central time touches **six UTC dates**. Worst case is cap x 6 dates x about $0.45 a run: a cap of 3 is about **$8.1**, within the $13 left; a cap of 6 would be about $16.2, more than is left, and a cap of 10 about $27. The built-in default is **3**.
- [ ] **Provider spending limit (owner, in the provider console):** $20 or lower for the pilot. This is the only hard guarantee; **confirm in the console whether the limit is monthly, per workspace or per key** (this document does not know the console's wording). No value or key goes in this file. The fastest hard stops are the provider limit or removing the key.
- [ ] **Safe defaults (built in):** `daily_cap` 3, `rate_limit_per_hour` 3 per visitor, `max_judgments` 15. Check with `GET /api/admin/settings` and `GET /api/admin/environment`; the old defaults (200 a day, 20 an hour, 25 judgments) could spend about $88 in a day if a public link were shared. An existing database keeps any value already saved in its settings table, so check there too.
- [ ] **Prices in settings (estimates, on by default):** `price_per_mtok_input` 4.0 and `price_per_mtok_output` 20.0 are built in, so cost is recorded and the application budget stop is active out of the box. They are ESTIMATES: list prices for `claude-opus-5-5`, cached 2026-11-03. The owner confirms them in the provider console and can change them with `PUT /api/admin/settings`. If both are set to 0, `cost_usd` stays empty and the budget stop is inactive (the environment report then says so).
- [ ] **Application budget stop:** setting `pilot_budget_usd` (default **9.0**, send decimals). Once the sum of recorded run costs (`runs.cost_usd`, failed runs included, because they still spend tokens) reaches it, new live runs are refused with a plain message (`budget_reached`) and the recorded example run is offered instead. It reads the database, so it survives restarts. `GET /api/admin/environment` reports `budget_stop`: the state (`active`, `reached` or `inactive: ...`), the limit, the recorded estimate, the prices in use and what is counted. **It counts only the runs in this database, not the roughly $7 of earlier engineering spend**: $7 already spent + $9 here + about $1.5 of rehearsal checks stays under $20 with margin. It also undercounts calls that were abandoned. The provider limit stays the real guard.
- [ ] **Reading the cost after each run:** `counters.cost_usd` in the run response (an estimate; `cost_basis` says so); the admin run list and `GET /api/admin/runs.csv` (column `cost_usd_estimate`). Sum that column for the spend so far; treat the real spend as a little above it and compare with the provider console.
- [ ] **Spend tally:** one running line with the owner (date, runs, sum of `cost_usd_estimate`, console figure). Check it before any batch of runs.
- [ ] **Recorded run for the public pages:** ONE real run, from a CLEAN checkout of the merged integration commit (the script refuses to spend when `git status --porcelain` is not empty, so the commit id in the file is true), on a fictional researcher, made with `scripts/record_run.py` (about $0.45) only after the project manager and the architect approve. It needs `--price-in` and `--price-out` so the cost is recorded, and typically makes 15 to 17 calls, at most about 30 (about $0.9). It writes the unedited output with its run id, model, rubric version (the real hash), code commit, retrieval date, counters, the exact input, an empty `redactions` list and `deadline_flags_as_of`, and exports the run's logged detail next to the file, with its sha256 recorded in the file. Quotes are re-checked against the stored source text (it reuses the pipeline's matching, so it catches a source mismatch, not a defect in that function). `python scripts/record_run.py --verify --out FILE` re-checks a written file, and its exported detail, for edits at no cost. The results hash only detects accidental edits (anyone can recompute it), so **the commit that adds the recording must carry the run-detail sha256 and the code commit id in its message**; the architect reads the file and the run-detail export before they are committed.
- [ ] **Scripts that spend money** (`bench_judging`, `repeatability`, `model_check` in live mode, `record_run`) print the planned number of calls and an estimated cost and do nothing unless `--yes-spend-money` is given. Do not add the flag without the approvals in this section.
- [ ] **Stop points:** the project manager warns the owner at about $13 estimated, and asks again at $16. **At about $15 estimated, set `daily_cap` to 0 and ask the owner**; at $18 all live calls stop unless the owner says otherwise. Switch visitors to the recorded run (`live: false` in the pages' `config.js`).
- [ ] **Limits of a stop (know these):**
  1. `daily_cap` 0 does **not** stop runs already in flight; they finish, up to the 90-second judging deadline plus calls already running.
  2. The cap check is count-then-start, not atomic, so simultaneous requests at the cap can each pass; keep the cap below the budget by a margin.
  3. The daily count resets at UTC midnight, which is 18:00 Central during Dec 2 to 6, so a cap of 3 allows 3 more runs after 18:00 Central; account for that when sizing it.
  4. Setting `active_model` to `mock` also spends nothing, but live runs then fail with 502 instead of the daily-limit message.
- [ ] **Not allowed without the owner's approval:** model changes, the larger repeatability check (about 500 calls, roughly $15, declined), and any engineering run against the live model. After ANY live call, report the calls, tokens and dollar estimate to the project manager with a running total.

## 3c. Running live: the owner on their own computer, approved testers on the hosted engine
Variable names only; never write a value, key or access code into this file, a chat or a commit. Public visitors see the recorded run; only the owner and approved testers (each with an access code) run live. **Every live run, wherever it happens, spends the same $20 budget** (section 3b).
**Tester access codes (hosted engine)**
- A live run needs a code in the `X-Access-Code` header; without one the API answers 403 `missing` and the page offers the recorded example. Setting `require_access_code` (default `true`) turns the requirement on or off. Calendar, spreadsheet and email downloads, the pages and `/config.js` need no code.
- **Before creating codes:** `FORGE_SALT` must be set on the host (creating a code is refused without it). Changing `FORGE_SALT` later makes every existing code invalid.
- **Before giving any code to anyone:** (1) `GET /api/admin/environment` must show `access_codes.required: true` and `salt_set: true`; (2) the admin token must be a random string of 32 or more characters (on a hosted database a shorter one disables the admin API); (3) `FORGE_SALT` must stay stable from now on: changing it invalidates every access code AND every visitor hash (rate limits and run ownership), so set it once and keep it; (4) decide the expiry deliberately: the default `2026-12-08` means the START of that day in UTC, which is 18:00 Central on Dec 7, not the end of the pilot; send an explicit `expires_at` if you want a different moment.
- **Create a code** (your own terminal): `curl -X POST $HOST/api/admin/access-codes -H "X-Admin-Token: $ADMIN_TOKEN" -H "Content-Type: application/json" -d '{"label": "tester 1", "allowance": 3}'`. The answer shows the code ONCE (`fsa_...`); copy it and send it to that tester privately, then close the terminal output. It is stored only as a keyed hash, so it cannot be shown again; if lost, revoke and create a new one. One code per tester. The label must not be a real name or an email (`tester 1`, `tester 2`). `allowance` is the number of live runs (default 3, 1 to 20). `expires_at` defaults to the setting `access_code_default_expiry` (2026-12-08, the start of that day UTC, which is 18:00 Central on Dec 7); send `"expires_at": "none"` for no expiry. Create a code for yourself the same way: **allowance 2**, because with `pilot_budget_usd` 9.0 and about $0.45 a run exactly 20 runs fit (6 testers x 3 + your 2 = $9.00); creating a code that would exceed the budget is refused with a message (409 `budget_would_be_exceeded`) unless you deliberately raise `pilot_budget_usd` after checking the provider console. Revoking an unused code or using runs frees budget.
- **See usage and cost per code:** `curl $HOST/api/admin/access-codes -H "X-Admin-Token: $ADMIN_TOKEN"` lists each code's label, allowance, `runs_used`, `remaining`, expiry, whether it is revoked, `runs` and `cost_usd_estimate` (estimate). The code itself is never shown. The admin run list and the CSV have an `access_code_id` column.
- **Revoke:** `curl -X POST $HOST/api/admin/access-codes/<id>/revoke -H "X-Admin-Token: $ADMIN_TOKEN"` (the id comes from the list). It takes effect on the next request and can be repeated safely.
- One live run at a time per code: a second at the same moment gets a plain 429 `run_in_progress` message. Only FAILED code attempts are counted (about 20 an hour per visitor address, in memory), then that address gets 429 `too_many_attempts`; no code is ever locked. The researcher lookup also needs a valid code (it is checked, and never uses an allowance).
- On a hosted database an `ADMIN_TOKEN` shorter than 32 characters disables the whole admin API (503), so set a long one before creating codes.
- **Run ownership uses the visitor address hash:** a tester whose address changes mid-session (switching from Wi-Fi to a phone, for example) loses access to their own calendar download for that run; tell testers to download before switching.
- A run that fails with nothing spent (the model or the funding source is down) gives the tester the run back; a run whose answers were unreadable does count, because tokens were spent.
- `GET /api/admin/environment` shows `access_codes`: whether codes are required, whether the salt is set, how many codes are still usable, and `budget_reservation`: the runs still allowed, the committed estimate in dollars (runs times the estimated cost per run), the recorded spend and the total against `pilot_budget_usd`.
- **The proxy-hops rehearsal comes BEFORE any code is issued.** Failed code attempts are counted per visitor address (about 20 an hour). Testers behind one campus or office address share that counter, and a wrong `FORGE_TRUSTED_PROXY_HOPS` (unset behind a proxy, or too small) makes ALL visitors look like one address, so one person guessing wrong codes could make every tester get 429 `too_many_attempts` for an hour. That is a denial of service, not a way in (the codes themselves are never locked and cannot be guessed), but it would stop the pilot. A value that is too large lets a forged `X-Forwarded-For` dodge the limit. Prove the value in the rehearsal (section 3b/proxy steps in `backend/README.md`) first.
- **Production stays at ONE server worker.** The in-flight set (one run at a time per code), the failed-attempt counters, the researcher-lookup limits and the daily lookup cap all live in each process's memory; with more than one worker each would have its own, and the one-run-per-code rule and the limits would not hold.
**What to do when the budget stop is reached:** live runs answer 503 `budget_reached` with a plain message and the page offers the recorded run. Do not raise `pilot_budget_usd` or the allowances without asking the owner; check the provider console first. Revoke unused codes or set `daily_cap` to 0 to stop everything quickly.
**Run the engine on your own computer (the key never leaves it)**
1. From the repository's `backend/` folder: `pip install -r requirements.txt`.
2. Set the variables **in the terminal session, not on the command line** (macOS or Linux `export NAME='...'`; Windows PowerShell `$env:NAME='...'`). Never `echo` them or paste them into chat: `FORGE_API_KEY` (the model key), `ADMIN_TOKEN` (a long random string), `FORGE_SALT` (a different long random string), `FORGE_DB` (for example `forge.db`, a local SQLite file).
3. Fill the opportunity library once: `python scripts/ingest.py` (public Grants.gov data, no model, no cost, about a minute).
4. Start the server: `uvicorn --factory app.main:create_app --port 8000`. Without `--host` it listens only on your own computer (127.0.0.1). Do not add `--host 0.0.0.0` unless you mean to share it.
5. Switch the model on (the default `mock` cannot rate anything) and, for your own local use, turn the code requirement off (or create a code for yourself): `curl -X PUT http://localhost:8000/api/admin/settings -H "X-Admin-Token: $ADMIN_TOKEN" -H "Content-Type: application/json" -d '{"active_model": "claude", "require_access_code": false}'`. Check with `GET /api/admin/environment`: `active_model` is `claude`, `model_key_variable` names the variable you set (never its value), `budget_stop.state` is `active`.
6. Open `http://localhost:8000/`. The pages served by this server run live; the published static site keeps showing the recording.
7. Stop the server when done (Ctrl+C) and unset the key in that terminal (`unset FORGE_API_KEY`; PowerShell `Remove-Item Env:FORGE_API_KEY`).
**Check the cost after each live run** (ask before going past $20)
- The run response has `counters.cost_usd` (an estimate; `cost_basis` says so), the tokens and the time. A run takes about 20 to 25 seconds at 15 judgments and costs about $0.45 (estimate at $4 and $20 per million tokens).
- `budget_stop` in `GET /api/admin/environment` shows the recorded estimate so far **in that database only**: your local runs are in your local database and the hosted engine does not see them. Keep your own running total across both, and compare with the provider console, the real figure.
