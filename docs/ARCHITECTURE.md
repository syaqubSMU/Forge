Basis: code read at commit db17872 on `claude/practical-franklin-ze9hk2`, `docs/PRD_v0.2.md`, `docs/SIGNAL_BOUNDARIES.md`, `backend/README.md`. What was run is listed in section 9; everything else is from reading code.

## 1. Components

```
 Browser (static pages)            FastAPI engine (backend/app)                 Outside services
 public/signal/*.html, app.js ---> /api/runs, /api/runs/{id}/calendar... ----> Grants.gov public API (list + detail)
   config.js: live true/false      /api/admin/*  (X-Admin-Token)               Claude API (model adapter)
   sample mode = mock-data.js      pipeline.py  -> adapters/ -> validator.py   OpenAlex (PI lookup; P3 in review,
   run kept in sessionStorage      rubric.py, calendar.py, exports.py            host allowed by the owner 24 Nov)
                                   store.py (stored Grants.gov copy)
                                   db.py ------------------------------------> SQLite (local) or Postgres (Neon)
```

- **Pages**: seven static pages. With `live: false` (GitHub Pages) they show a fictional sample run and call nothing. With `live: true` they call the API. When the engine serves the pages itself it answers `/config.js` with `live: true`, which wins over the static file because API routes are mounted before the static folder.
- **Engine**: one FastAPI process. A run is one synchronous HTTP request.
- **Database**: one schema in SQLite or Postgres: run log (runs, matches, citations, source failures, email events, annotations), admin settings, audit trail, rubric versions, the stored Grants.gov copy (`opportunities`, `api_calls`).
- **Model**: behind `ModelAdapter`; the admin setting `active_model` picks the adapter for the next run. `mock` is the default and costs nothing.

## 2. Run data flow and trust boundaries

1. **Browser to API** (untrusted input). Visitor supplies name or text, research areas, career stage, rules, options. Validated by pydantic (length limits on `input_text` and some list sizes), per-visitor hourly limit and daily cap, option range checks.
2. **Source** (untrusted text). Stored Grants.gov copy, or a live pull until the first ingest. Sponsor text is untrusted: it goes into the model prompt.
3. **Shortlist** (plain code). Deadline window, then word-overlap ranking to bound spend. Not a fit judgment.
4. **Judge** (model, untrusted output). Threads call the adapter in parallel; the model returns factor values with quotes as JSON; the schema parser rejects anything else (one retry, then a recorded failure).
5. **Validate** (plain code). A quote must appear in the source text it names, or it is discarded and counted. A factor without a supported quote falls back to the rubric's conservative default.
6. **Rate** (plain code). `rubric.evaluate` computes the tier and word. Dates, days-to-deadline, internal deadline, calendar groups and exports are code.
7. **Log** (main thread only). Run, sources (hash only), matches, citations, failures, tokens, timing.
8. **API to browser**. No raw source text goes to the public; the run response carries the quotes, which are short extracts.

Trust boundaries: (a) browser to API; (b) API to Grants.gov and to the model provider (outbound, secrets leave only as the model key to the model host); (c) API to database; (d) admin token holder to admin API. The model key is read from server environment variables only. Residual risk named plainly: an injected instruction inside sponsor text could push the model to report a factor value and then quote the injected sentence, which the validator would accept because the sentence is in the source. The defences are the fixed rubric, code-computed tiers, conservative defaults for unsupported claims and mandatory human review; there is no technical block on this. Grants.gov is a federal source, so the risk is low for the demo and higher for any future pasted or non-federal source.

## 4. Decision records

### DR-1 Reversing "no stored opportunity index" (**Decided** for the demo; wording merged)
Context: PRD D4 and hard rule 1 said no opportunity database; live pulls were slow and the 72 s full ingest showed a stored copy is cheap. The customer approved storing the Grants.gov corpus for the demo.
Decision: store the sponsor's public records and cleaned text (`opportunities`), with retrieval times, and stamp each result with the retrieval time. Researcher profiles and judgments are never stored in these tables; the profile exists only inside that run's log record.
Consequences: the PRD wording and the `db.py` docstring now record the reversal (both merged). `docs/SIGNAL_BOUNDARIES.md` never mentioned an opportunity index and needed no change. The stored copy goes stale: it is refreshed by `scripts/ingest.py` or the admin button, and runs show "retrieved at". Retention (90 days) applies to the run log, not to the opportunity copy; say so on About if the owner wants it stated (**Open**).

### DR-2 Parallel judging and model effort (**Decided** and merged; cheaper model and low effort **Open**)
Decision (merged): judge shortlisted opportunities in a bounded thread pool (`judge_concurrency`, default 8, hard cap 16); a process-wide cap on simultaneous model calls (`FORGE_MODEL_MAX_CONCURRENT`, default 16); an overall judging deadline (`judge_deadline_s`, default 90) after which no new paid call starts; only the main thread writes to the database, in ranked order; the SDK retries 429 and overload with backoff. A run in which nothing could be rated because of the model (calls failed or every answer unreadable) is failed with HTTP 502, not shown as an empty result. The output cap is 3,000 tokens (`FORGE_MAX_OUTPUT_TOKENS`); 1,500 had cut about 1 in 25 answers mid-JSON.
Evidence (engineer's live measurements, single samples, in `backend/README.md`): 25 judgments at default effort took 43.5 s on 8 workers and 21.8 s on 16 workers with the new cap (25 of 25 judged); sequential would be about 230 s. Under 30 s holds only at about 16 workers, which is also the global cap, so a second simultaneous run queues and takes longer. No 30 s promise belongs in copy or slides.
Decided by the project manager on the engineer's recommendation (25 Nov): the demo uses the model's default effort, a global cap of 16 concurrent model calls (sequential testers), the 3,000-token output cap and the 90 s judging deadline.
Closed by the owner (25 Nov): the cheaper model is off the table for the pilot and the larger repeatability check is declined; each live run screens 15 opportunities (`max_judgments` 15). Still open: the production global cap should come from the key's rate limits and a rehearsal with two simultaneous runs. Production runs ONE server worker because every cap, limiter and cache is per process. See DR-8 for the budget that now governs all of this.

### DR-3 Retrieval (**Decided** and merged: BM25; embeddings **Open, deferred**)
Merged: BM25 over title (weighted 3x) and text against the research areas only; records sharing no term with them are not sent to the model and are counted (`no_term_overlap`); two-letter capitals such as AI and ML count; the detail cap is lifted when reading the stored copy, with stored details read in chunks of 200 ids. Evidence: `scripts/retrieval_check.py` on a frozen snapshot of 787 records, mean recall@10 0.26 to 0.75 and MRR 0.51 to 1.00 on 6 queries labelled by one AI rater. This is weak evidence (few queries, unreviewed labels biased toward keywords, parameters untuned but not independent of the labeller's skim) and is not an accuracy figure; a person must review and extend the labels before any figure is quoted outside the repository. Synonym-only matches are missed by design. The Results page must show the no-overlap count and reason (UX, pending). Embeddings stay deferred: they add a provider, cost and a second index and cannot be evaluated until reviewed labels exist. The engineer's own short records are in `docs/BACKEND_DECISIONS.md`.

### DR-4 PI lookup (**Decided** for the API, merged; the page flow **Open**)
Merged: `POST /api/pi/search` (the name travels in the body) and `GET /api/pi/{id}/expertise`, server-side calls to OpenAlex (allowed by the owner on 24 Nov) with a generic client name, no key and no email; answers cached in memory only; per-visitor and daily limits; a written error table; the call log keeps only the name's length and a keyed HMAC of the author id. Design rule that the pages must follow: the person picks a candidate, sees proposed terms with the works that produced them, edits and confirms them before any run; terms are used for that run only and not stored. The page must also say that the typed name is sent to OpenAlex. Disambiguation stays a human choice (similar names are shown separately, never merged). The manual research-areas box remains the fallback. No page uses these endpoints yet (**Open**, UX).

### DR-5 Schema versioning (**Decided** and merged)
Numbered migrations in `app/migrations.py`, each applied once in its own transaction, recorded in `schema_migrations`, with a Postgres advisory lock so two starting servers cannot race. Version 1 adopts the existing schema; version 2 adds `cost_usd`. Verified by the architect: a failing migration rolls back completely on SQLite and Postgres; four simultaneous starts on an empty Postgres succeed. Rules: migrations are additive while an old and a new server can overlap during a deploy; on Neon use the direct (non-pooled) connection string because session advisory locks do not work through the pooler; pass the address through `FORGE_DB`, never `--db`. `scripts/migrate.py` reports the version without printing the address; `scripts/db_smoke.py` is for a dev database only.

### DR-6 Hosting (**Proposed**, accounts **Open**)
Plan: Render for the engine, Neon for Postgres, GitHub Pages for the static sample pages. Requirements for the engine behind Render's proxy: start uvicorn with forwarded headers trusted for the platform proxy, or every visitor will appear to come from one address (see review notes: rate limits and run ownership use the client address). Set `FORGE_SALT`, `ADMIN_TOKEN`, the model key and `FORGE_CORS_ORIGINS` as service environment variables. Confirm the platform's request timeout against the longest run. Free-tier cold starts and Neon scale-to-zero add seconds to the first request; the code already reconnects once on a dropped connection.
Governance: SMU's expectations for a hosted app (accessibility, SSO, data protection, ownership, maintenance) apply; run the `app-hosting-self-review` skill with OIT before wider use, and ask OIT whether this duplicates an existing research-administration system.

### DR-7 Run is one synchronous request (**Open**)
A run holds a request open for tens of seconds. It is the smallest design that works. The alternative (start a run, poll its status) gives real progress, survives proxy timeouts and lets a browser stop waiting without losing the result, at the cost of a background worker and a status table. Recommendation: keep synchronous for Dec 2; revisit only if the platform timeout or measured run times require it.

## 5. Security and data controls (current state)
| Control | State |
|---|---|
| Model key | Server environment only; never returned or logged (tests cover the exception text path). |
| Admin | Single shared token, constant-time compare, disabled when unset, no throttle on failed attempts (**Open**: a lockout with doubling delay was proposed and deferred by the project manager until after the hosted rehearsal, because a wrong `FORGE_TRUSTED_PROXY_HOPS` value would let one attacker lock out the owner or let a forged header dodge the limit); the server warns at start if the token is shorter than 32 characters. |
| Public limits | Hourly per visitor, daily cap on runs. Cost bound is daily cap x `max_judgments` model calls. |
| Input size | `input_text` 4000, `question` 1000, profile lists and item lengths capped, pasted sources 3 x 20,000 characters, public POST bodies limited (default 400,000 bytes, Content-Length required). |
| Client address | Socket peer unless `FORGE_TRUSTED_PROXY_HOPS=N`; then the Nth entry from the right of X-Forwarded-For. A value that is too large makes the address client-controlled, so the dev rehearsal must prove a forged prefix is ignored (`/api/admin/whoami`). The Render value is **Open**. |
| CORS | Off unless `FORGE_CORS_ORIGINS` is set. |
| Exports | Formula-injection protection in CSV and spreadsheet output. |
| Run log | Inputs, citations (short quotes), counters; source text is hashed, not stored. 90 days then archived (archived rows are kept; deletion policy **Open**). |
| Data classes | Public and Private only; notice on the pages; no Restricted data. |

### DR-8 Pilot budget and the recorded run (**Decided** by the owner 25 Nov; budget stop and recording **built and approved**; live access rule below)
Owner constraints (relayed by the project manager; prices are the model list prices cached 2026-11-03 and have not been re-checked by the architect): the whole pilot costs under USD 20 including about USD 7 already spent (an estimate); `claude-opus-5-5` at USD 4 per million input and USD 20 per million output tokens; live model calls only when important; one real run is recorded and served by the public pages so testers see real output at no cost; assume a pilot of Dec 2 to 6.
Arithmetic (architect, from the engineer's counters in `backend/README.md`: 25 judgments used about 33,700 input and 31,900 output tokens): about USD 0.77 for 25 judgments at those prices (the owner's estimate is 0.73), about USD 0.44 for 15. The remaining budget of roughly USD 13 is therefore about 29 runs of 15 judgments with nothing else spent, and the logged cost excludes abandoned or failed calls, so plan for fewer than 29.
Consequences for the design:
1. The default `daily_cap` of 200 runs would allow about USD 88 a day. Safe hosted defaults are required before any public address exists: a daily cap of single digits, a lower hourly limit, `max_judgments` 15. The provider-side spending limit set by the owner is the real guard; application caps are the second.
2. Proposed: an application budget stop. Enter the model prices in settings so `cost_usd` is recorded; add a pilot budget setting (total USD) and refuse new live runs, with a plain message and the recorded run offered instead, once the recorded estimate reaches it. The stop uses an estimate that undercounts abandoned calls, so set it below the provider limit.
3. The public default is the recorded run, never a live call. Live runs are for named testers or the owner, behind an explicit switch (design **Open**: an access code or admin-enabled window; the owner decides who may spend).
4. Rehearsals that call the model cost money too and come out of the same budget; the hosted rehearsal should use the mock model except for the one or two live checks that matter.
Recorded run integrity rules (architect position, **Decided**; applied in the recording and the pages): the recording is the unedited output of one real run, kept with its run id, retrieval date, model, rubric version and counters; the page says it is recorded and when, never "live" and never "your result"; the input shown is the input that produced it; days-to-deadline and "passed" flags are shown as of the recording date (or recomputed from the stored close dates with the as-of date stated); a visitor who types a different researcher must not be shown the recorded result as if it answered that input; the profile used is fictional or de-identified, or the person has consented to appear; one recorded run is a demonstration, not evidence of accuracy, and the copy must not say otherwise.

Status as of 25 Nov (owner decisions relayed by the project manager): the safe defaults (daily cap 3, 3 runs an hour per visitor, 15 judgments), the application budget stop (`pilot_budget_usd` 9.0, prices 4.0 and 20.0 as estimates, counts only the database it reads, mock runs cost nothing, failed runs keep their cost) and the spend guard on the scripts are merged. One real run was recorded on a fictional researcher (run id 6790215da1be4254867d055862a987a4, 15 judged, estimate USD 0.48, reviewed and merged as data); the pages that show it are approved with conditions and not yet merged.
Owner decisions: (1) Release to `main` is authorized once the architect and the project manager have approved the recorded-run pages and the project manager has re-tested the final head; the public site then becomes the new design with the recorded run clearly labelled. (2) The owner directed and approved the UI/UX redesign (closes the open item). (3) Eligibility: the recording stays as it is for Dec 2; checking the institution type against the structured applicant types is a next-version item. (4) Live access (corrected by the owner 25 Nov): the owner and testers the owner approves may run live searches against the model budget during Dec 2 to 6; everyone else sees the recording. Design in DR-9.
Architect assessment of (4): the public GitHub Pages site stays static (`live: false`), calls no backend and cannot spend anything. Approved-tester access needs a backend testers can reach, so "only approved testers" must be a control, not a convention: any reachable backend accepts `POST /api/runs` from anyone who finds its address. See DR-9.

### DR-9 Approved-tester access to live runs (**Decided and built**; open-window amendment **Proposed**; architect review of the project manager's design, 25 Nov)
Design: the owner creates per-person access codes through admin endpoints; `POST /api/runs` (both the live and the pasted-sources path) requires a valid code in an `X-Access-Code` header, otherwise 403 with a plain message that offers the recorded example; every run records which code made it; the global daily cap, the hourly limit and the pilot budget stop still apply on top. The hosted engine serves the pages at its own address (same origin, `live: true`); the GitHub Pages site stays recorded-only.
Architect additions: codes are at least 128 bits of randomness (for example 26 base32 characters, shown once) and stored only as an HMAC-SHA256 with a domain-separated key (the server salt), never the code; the lookup is by that hash. Allowance is consumed atomically before the run starts with one conditional update (`used < allowance`, not revoked, not expired, rows affected must be 1), refunded only when the run fails before any model call; one run in flight per code. Budget reservation: creating a code is refused if the allowances still outstanding, at the estimated cost per run, plus recorded spend would exceed `pilot_budget_usd`, so the number of codes times the allowance is bounded by the budget before anyone searches. Codes are per person (attribution, revocation, a leak costs one allowance), labelled with a non-name label (reject '@'; guidance not to use real names), with an expiry set to the end of the pilot. The run row stores only the code's numeric id; the code and its hash never appear in a log, a response, an admin list or an audit entry; failed codes are counted per client address in memory, not logged or stored. A failed-attempt throttle is not needed for security with 128-bit codes; a cheap per-address limit on failures (for example 20 an hour, then 429) keeps noise out and must only slow, never lock a code; it depends on `FORGE_TRUSTED_PROXY_HOPS` being right, otherwise all visitors share one address and one attacker can block testers (not gain access), so the hops value is rehearsed first. The deferred admin-token throttle stays deferred; with a public address the admin token must be 32 or more random characters, and a hosted database with a shorter token should leave the admin API disabled.
What the public address exposes: the static pages; `/api/health`, `/api/notice`, `/config.js`; `POST /api/runs` (403 without a code); admin endpoints (401 without the token); the researcher-lookup endpoints if enabled (they spend no model money but call OpenAlex and should also require a code). Codes travel only in a header over HTTPS, are kept by the page in the browser tab only (session storage, never a URL), and must be entered on Find funding with a visible "see the recorded example" alternative (UX work). The daily cap is then pacing, not the ceiling: the ceiling is the budget stop (about 20 runs of 15 judgments in total from the remaining budget), so size codes and allowances to it, for example six testers with an allowance of 2 or 3.
Tests (fakes only, SQLite and Postgres): atomic allowance under concurrent threads, revoked and expired codes, 403 text, the code and hash absent from every response and log, the admin list never showing them, the budget reservation refusal, the budget stop still firing, a run created without a code refused on both paths.

Amendment (owner decision 25 Nov, relayed by the project manager): live searches also stay open to everyone during the DEMO WINDOW, because the course rubric requires the product link to be publicly accessible without logging in and graders must be able to test it. Plan: before the window the owner sets `require_access_code` to false with `daily_cap` and `pilot_budget_usd` small enough to bound spend (about USD 0.45 a run); the budget stop answers 503 `budget_reached` and the pages offer the recorded example; afterwards `require_access_code` goes back to true and a separate grader code (3 runs) is created for the report; accepted risk: anyone with the link can use up the daily cap before the presentation, so the window opens close to presentation time and the count is checked right before.
Architect assessment. The plan is safe for money (the ceiling is the daily cap, the budget stop and, above all, the provider-side hard limit, which the owner must set before the window opens), but it has one real weakness: a public cap shared with the owner and graders lets anyone lock them out of the live product at the moment it matters, and public runs can consume the budget that the owner's and the grader's codes were reserved against. Alternative for the record: the recorded example is already public without any login and satisfies "publicly accessible"; the owner has decided on open live access, so the following protections are proposed instead of a different plan.
Proposed protections (small, for the engineer, with tests on SQLite and Postgres): (a) a code is honoured whenever it is sent, even when codes are not required: valid code, claim the allowance and use it; invalid, 403; no code, a public run; (b) two limits: `public_daily_cap` counts only runs without a code (for example 4), `daily_cap` stays the overall pacing figure and must be larger (for example 12), so a public rush can never block code holders; (c) a public run is refused when recorded spend plus the runs still reserved to usable codes plus one run would exceed `pilot_budget_usd`, so reserved allowances cannot be eaten by the public; code holders are refused only when recorded spend has reached the limit; (d) the environment report shows today's runs (public and coded), the remaining public capacity and the committed estimate, so the count can be checked right before the presentation; (e) the researcher-lookup endpoints without a code keep their per-address and daily limits, tightened for the window (for example 20 an hour per address and 200 a day), since they spend no model money; (f) the page: when codes are not required the Access card stays hidden by default but offers an "I have an access code" link, and the daily-cap, public-cap and budget messages always offer the recorded example and say that codes still work; no "no code needed" state is required beyond that.
Operating rules for the window: the owner sets the provider limit first; opens the window close to the presentation; checks `GET /api/admin/environment` (access_codes.required false, caps, budget_stop, reservation) and the day count immediately before; keeps `FORGE_TRUSTED_PROXY_HOPS` verified so per-address limits mean something; closes the window by setting `require_access_code` true and, if the cap was hit, reads the run list for abuse; the owner's own presentation run uses an owner code. Anything typed by the public is logged for 90 days and goes to the model: the page notice (public and private data only, no Restricted data) must stay visible, and the OIT self-review remains open.
